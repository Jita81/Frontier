# EXP-05: Can a new star base be added to a system, and can you fly there, dock and trade?

## Question

Can the host add a new starport to a system, behind a default-off flag, so that:
- it appears in the right place, orbiting its planet, on the game's own maps;
- you can fly to it, get clearance and dock;
- it works as a station: services, bulletin board with missions, stock market;
- it is consistent with the system's economy, allegiance and population;
- every other system is byte-identical, with the flag on or off?

And which route should production take: editing a save file, a runtime overlay from the host, or a new host call?

## Method

1. **How `fe2.s` resolves a system's starports.**
   - The sysgen module (L4655a) builds a fresh list of 64-byte body records on the stack **every time** a system is needed: arrival, system map, system data screens. There is no lasting list in RAM or in the save file to edit.
   - Procedural systems are rolled from the system seed (starports by L47164).
   - Hand-made systems (Sol, Alpha Centauri, Ross 154, …) take the path at l473ec. It looks the system id up in a table of (id, offset) pairs at L47390 and expands the 64-byte source records found at that offset, up to a terminator record. A record holds the orbit, seeds, the 1-based index of its parent body, the body type, the model, and the name. Types 0x40, 0x42 and 0x44 are orbital stations; 0x46 is a surface starport.
   - The record layout is documented in the header of `src/expbase.c`.
2. **The three routes.**

   | Route | Verdict |
   |---|---|
   | Edit the save file | Not viable. Sysgen regenerates the bodies on every request, so a station written into a save is never read back. |
   | Runtime overlay from the host | Works with no `fe2.s` change, but only for hand-made systems, which have a source table to redirect. **Prototyped.** |
   | New host call at the end of sysgen | Works for every system, procedural included. Needs a small `fe2.s` patch. **Recommended for production.** |

3. **The prototype: `FE2_NEW_STARPORT=1`** (`src/expbase.c`, 146 lines). At start-up, before the first 68k instruction:
   - it finds the L47390 table by its signature, and the Ross 154 and Wolf 630 entries in it;
   - it checks what it expects to find: Ross 154's first record is named "Ross 154", the planet "Merlin" exists, Wolf 630 has "Mayflower High" of type 0x42, and the overlay RAM at 0x84000 (above the program image) is all zero. If any check fails, it logs why and stays off;
   - it copies Ross 154's 7 records to 0x84000, appends one station record and the original terminator, and points Ross 154's table entry at the copy.
   - The new record is the game's own record for **Mayflower High**, an orbital station around Landfall, a planet of the same body type as Merlin. Only the parent (Merlin, index 4) and the name change. " High" is the game's own suffix for a station named after the body it orbits (Mars High, Mayflower High), so the station is **Merlin High**.
   - Economy, allegiance and population are system-level values that sysgen does not take from body records, so the station inherits Ross 154's. Its market, missions and traffic are generated by the game's own code, exactly as for an original station.
   - The new harness command `memdump` writes all of ST RAM to a file. `click l|r [n]` now holds the button for n frames.
4. **Runs.** All from the standard start (docked at Sirocco Station, Ross 154). Scripts are in [`capture-script.txt`](evidence/E05/capture-script.txt).

   | Run | Flag | What it tests |
   |---|---|---|
   | e5b, e5off | on, off | galactic map and F5–F9 system screens for Ross 154 |
   | e5d, e5doff | on, off | system map (orrery), zoomed in step by step on Merlin |
   | e5k | on | target Merlin High, launch, autopilot, approach, clearance, docking, services, bulletin board, equipment (e5i and e5j were shorter first tries of the same flight) |
   | e5m | on | Merlin High's stock market |
   | e5s | off | Sirocco Station's stock market, for comparison |
   | e5u_{barn,gic}_{on,off} | on, off | two unrelated systems, Barnards Star and Giclas 158-27, selected on the galactic map: map, F6, F7, F8, orrery; RAM dump at frame 1 |
   | e5u_{barn,gic}_e4 | E4 binary (20a9aab) | same script, pre-E5 baseline |
   | e5u_{barn,gic}_base0 | first harness binary | same script, older baseline |

   The galactic map does not select a star on a harness mouse click, so the unrelated systems are selected by scrolling the map with the arrow keys until the system is nearest the centre.

## Result

**PROVED.** With `FE2_NEW_STARPORT=1` a new orbital station, Merlin High, orbits the planet Merlin in Ross 154: it is on the system map beside Merlin, the autopilot flies to it, traffic control clears the ship to a bay, it docks, and its services, bulletin board (with a passenger mission) and stock market all work, with the system's economy, allegiance and population unchanged. With the flag off every shot is md5-identical to the pre-E5 build, and two unrelated systems are md5-identical with the flag on.

- **Flag off.** On the unrelated-system script, off = E4 binary = first harness binary on all 6 shots × 2 systems, both as the `.st` buffer and as the window. E4 was shown identical to e508341 in EXP-04. With the flag off, the overlay RAM 0x84000–0x842ff is all zero and Ross 154's table entry is unchanged.
- **Unrelated systems, flag on.** For Barnards Star and Giclas 158-27, the galactic map, F6 (system diagram), F7 (trade) and F8 (government, economy, allegiance, population) are md5-identical on and off. Other systems' orreries cannot be shown without travelling there; the RAM check below covers that.

  - 232 bytes in the overlay at 0x84000–0x8423f: 7 copied records, the new one and the terminator.

  Nothing else in RAM changes, so every other system's records, and the expander, are untouched.

## Hook needed

**What exists now** is host side only:
- `src/expbase.c` (146 lines): finds the table, checks it, writes the overlay, logs one line;
- `src/exp.c`: `ExpBase_Init` at start-up, the `memdump` command, and the click hold length;
- `Makefile-C`: `expbase.o`.

When off, `ExpBase_Init` returns on the `getenv` test and RAM is never touched.

**A production version should change these things:**
1. **A `SysGenDone` host call** at the end of the sysgen expander (both the hand-made path and the procedural one), passing the system id and the address and count of the records it built. The host appends its own stations to the list there. This works for every system, needs no free RAM above the image, and keeps the game's own records as they are.
2. **A station file** of added stations: system id, parent body by name, station type (orbital or surface), name, and the record to copy. Validated on load: parent exists, name unique in the system, type is one the game knows.
3. **Persistence.** Stations are regenerated on every visit, so the station file is the persistence: it belongs with the save (a side file next to it), not inside the game's save format.
4. **Improving a station.** Upgrading means changing its record: a bigger model (orbital 0x40 → 0x42 → 0x44), or a surface starport. Station services and traffic follow the type. Anything beyond what the game's own types offer (new services, new markets) is new design, not this hook.
5. **Building one in game** (choosing a site, paying for it) needs new UI and a rule for what a player may change. That is also design work beyond this hook.

## Oracle implications

- **Flag off is the oracle build.** With the flag off nothing changes, so oracle runs should keep it off. With it on, any trace of Ross 154 differs from the original game by design.
- **Game state is changed, by design.** Unlike E1–E4, which change only pixels or sound, this hook changes what the game simulates: a new body, its traffic, its market and its missions. A parity oracle cannot compare a modded system to the original; it must compare only systems with no added stations, as the unrelated-system runs do here.
- **Fidelity check** (standing rule, 2026-10-25):
  - **The station never contradicts the game.** It is built from the game's own record for a station of the same kind around a planet of the same type, and named with the game's own naming rule. Its economy, allegiance and population are the system's: the F8 screen is pixel-identical on and off. Its market, missions and traffic come from the game's own code, which generated goods, prices and stock in line with the original station.
  - **Nothing else moves.** Two unrelated systems are md5-identical on and off, and RAM differs only in the one table entry and the overlay.
  - **Known gaps.** The orbit is copied from Mayflower High, not computed for Merlin's mass and radius, so it is plausible but not derived. A production station file should compute the orbit from the parent's data, or pick from the game's own stations around a body of the same type and size. The price spread between two original stations in one system is not measured yet.

## Legal flags

- **No FD asset is copied into the repo.** The overlay copies the game's own records at runtime, in RAM. The source holds only the table signature (8 bytes), two system ids and two names.
- **Station names.** "Merlin High" follows the game's naming rule. A station file shipped with a mod is mod content, distributed separately and loaded at runtime.
- **Screenshots and game text.** Kept outside git. The evidence quotes a few short in-game messages, within the "a couple of lines" rule.
- **Elite Dangerous.** Nothing from it was used.

## Effort to productionise

**M**:
- a `SysGenDone` host call at the end of both sysgen paths (a few lines of `fe2.s`), plus a check of every caller that walks the body list;
- the station file, its loader and validator, and saving it beside the save;
- computing the orbit from the parent body;
- tests: every system unchanged with an empty station file, and one added station in a procedural system.

**L** if building and improving stations in game is included, because that needs new UI and rules.

Phase 1 issues seen and not fixed:
1. A harness mouse click on the galactic map does not select a star, even held for 30 frames (the cause was not investigated). The arrow keys do select one.
2. A police event appears on docking at a new station, as it does in the original game.
